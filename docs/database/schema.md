# Database Schema

PostgreSQL 17 is the target database. Tests use SQLite by default for speed and
PostgreSQL through `TEST_DATABASE_URL` for parity.

All primary keys are UUIDs generated by the application. Every table except
`auth_sessions` uses a `created_at`/`updated_at` timestamp pair; timestamps are
timezone-aware in PostgreSQL and default to `now()`.

The schema currently has three revisions: `0001_initial` (Phase 1),
`0002_phase2_financial` (Phase 2) and `0003_phase3_intelligence` (Phase 3).
This document covers all three. See [Migrations](#migrations) for the current
applied state of the development database.

## Phase 1: identity and sessions

## `users`

| Column | Type | Constraints |
|---|---|---|
| `id` | UUID | Primary key |
| `full_name` | varchar(120) | Not null |
| `email` | varchar(320) | Not null, unique index, stored lowercase |
| `hashed_password` | varchar(255) | Not null, Argon2id hash |
| `is_active` | boolean | Not null, default `true` |
| `last_login_at` | timestamptz | Nullable |
| `created_at` | timestamptz | Not null, default `now()` |
| `updated_at` | timestamptz | Not null, default `now()` |

Indexes: unique `ix_users_email`.

Uniqueness is checked by the service before insert and enforced by the database.
A concurrent duplicate registration is caught as an `IntegrityError` and returned
as a `409 Conflict`.

## `user_preferences`

One row per user, created with the account.

| Column | Type | Constraints |
|---|---|---|
| `id` | UUID | Primary key |
| `user_id` | UUID | Not null, unique index, FK → `users.id` `ON DELETE CASCADE` |
| `currency` | varchar(3) | Not null, default `INR` |
| `timezone` | varchar(64) | Not null, default `Asia/Kolkata` |
| `theme` | varchar(16) | Not null, default `system`; allowed `system`, `light`, `dark` |
| `email_notifications` | boolean | Not null, default `true` |
| `push_notifications` | boolean | Not null, default `true` |
| `weekly_summary` | boolean | Not null, default `false` |
| `onboarding_completed` | boolean | Not null, default `false` |
| `created_at` | timestamptz | Not null, default `now()` |
| `updated_at` | timestamptz | Not null, default `now()` |

Indexes: unique `ix_user_preferences_user_id`.

Currency must be a three-letter alphabetic code. Timezones are validated against
the IANA database.

## `auth_sessions`

Each row represents one refresh-token session. Access tokens reference the row
through the `sid` claim.

| Column | Type | Constraints |
|---|---|---|
| `id` | UUID | Primary key |
| `user_id` | UUID | Not null, FK → `users.id` `ON DELETE CASCADE` |
| `refresh_token_hash` | varchar(64) | Not null, unique index |
| `expires_at` | timestamptz | Not null |
| `revoked_at` | timestamptz | Nullable; set on rotation, logout or account status change |
| `last_used_at` | timestamptz | Nullable |
| `user_agent` | varchar(255) | Nullable |
| `ip_address` | varchar(45) | Nullable (IPv4/IPv6) |
| `created_at` | timestamptz | Not null, default `now()` |

Indexes: `ix_auth_sessions_user_id`, unique `ix_auth_sessions_refresh_token_hash`.

The raw refresh token is never stored. Only its SHA-256 hex digest is persisted.
A session is active when `revoked_at IS NULL` and `expires_at` is in the future.

ORM writes of `users.is_active` revoke all of that user's sessions in the same
transaction, enforced by the account-status guard. Raw SQL and Core bulk
`UPDATE` statements bypass the guard and must be handled operationally.

## Phase 2: financial data

All Phase 2 tables carry `created_at` and `updated_at` (`timestamptz`, not null,
default `now()`; `updated_at` also updates on ORM change). Every table has a
`user_id` foreign key to `users.id` with `ON DELETE CASCADE`; ownership checks
are applied in the repository layer and every query is scoped by `user_id`.

### `bank_connections`

A consent-based link to a financial-data provider. The stored
`external_reference` is an opaque provider handle — never a password, PIN, OTP or
card security code.

| Column | Type | Constraints |
|---|---|---|
| `id` | UUID | Primary key |
| `user_id` | UUID | Not null, FK → `users.id` `ON DELETE CASCADE` |
| `provider` | varchar(32) | Not null |
| `institution_id` | varchar(64) | Not null |
| `institution_name` | varchar(120) | Not null |
| `external_reference` | varchar(128) | Not null, opaque provider reference |
| `status` | varchar(16) | Not null, default `active`; observed `active`, `revoked`, `expired` |
| `is_mock` | boolean | Not null, default `true` |
| `last_synced_at` | timestamptz | Nullable |
| `last_error` | varchar(500) | Nullable, safe message |
| `created_at`, `updated_at` | timestamptz | Not null, default `now()` |

Indexes: `ix_bank_connections_user_id`.

### `bank_consents`

The user's recorded consent for a connection. Multiple rows are allowed over
time; the latest by `granted_at` is authoritative.

| Column | Type | Constraints |
|---|---|---|
| `id` | UUID | Primary key |
| `connection_id` | UUID | Not null, FK → `bank_connections.id` `ON DELETE CASCADE` |
| `user_id` | UUID | Not null, FK → `users.id` `ON DELETE CASCADE` |
| `scopes` | varchar(255) | Not null; comma-separated scopes, `accounts,transactions` for the mock |
| `status` | varchar(16) | Not null, default `active`; observed `active`, `revoked`, `expired` |
| `granted_at` | timestamptz | Not null, default `now()` |
| `expires_at` | timestamptz | Not null |
| `revoked_at` | timestamptz | Nullable |
| `created_at`, `updated_at` | timestamptz | Not null, default `now()` |

Indexes: `ix_bank_consents_connection_id`, `ix_bank_consents_user_id`.

### `financial_accounts`

Accounts returned by a provider. A row can exist without a connection so that a
manual record set can be represented; Phase 2 only creates provider-backed rows
through the banking module.

| Column | Type | Constraints |
|---|---|---|
| `id` | UUID | Primary key |
| `user_id` | UUID | Not null, FK → `users.id` `ON DELETE CASCADE` |
| `connection_id` | UUID | Nullable, FK → `bank_connections.id` `ON DELETE CASCADE` |
| `external_id` | varchar(128) | Not null, provider account identifier |
| `name` | varchar(120) | Not null |
| `account_type` | varchar(24) | Not null; provider values are validated against `checking`, `savings`, `credit_card`, `loan`, `wallet` |
| `currency` | varchar(3) | Not null |
| `balance` | numeric(14,2) | Not null, default `0` |
| `available_balance` | numeric(14,2) | Not null, default `0` |
| `is_active` | boolean | Not null, default `true`; set false on consent revocation |
| `is_mock` | boolean | Not null, default `true` |
| `last_synced_at` | timestamptz | Nullable |
| `created_at`, `updated_at` | timestamptz | Not null, default `now()` |

Constraints and indexes:

- Unique `(connection_id, external_id)` —
  `uq_financial_accounts_connection_external`.
- `ix_financial_accounts_user_id`, `ix_financial_accounts_connection_id`.
- `ix_financial_accounts_user_active` on `(user_id, is_active)`.

### `transaction_categories`

Shared system categories (`user_id IS NULL`) and optional user categories.
System rows are inserted idempotently by `CategoryRepository`.

| Column | Type | Constraints |
|---|---|---|
| `id` | UUID | Primary key |
| `user_id` | UUID | Nullable, FK → `users.id` `ON DELETE CASCADE`; `NULL` means a system category |
| `slug` | varchar(48) | Not null |
| `name` | varchar(64) | Not null |
| `kind` | varchar(12) | Not null, default `expense`; values include `income`, `expense`, `transfer` |
| `is_system` | boolean | Not null, default `false` |
| `created_at`, `updated_at` | timestamptz | Not null, default `now()` |

Constraints and indexes:

- Unique `(user_id, slug)` —
  `uq_transaction_categories_user_slug`. Because system rows have a `NULL`
  `user_id`, uniqueness of system slugs is enforced by the idempotent seeding
  code rather than by this constraint (SQL treats `NULL` values as distinct).
- `ix_transaction_categories_slug`, `ix_transaction_categories_user_id`.

System slugs: `salary`, `refund`, `rent`, `utilities`, `groceries`, `dining`,
`transport`, `travel`, `shopping`, `entertainment`, `health`, `education`,
`fees`, `transfer`, `other`.

### `transactions`

Stored provider or manual transactions. `amount` is signed: positive is income
or a refund, negative is an expense.

| Column | Type | Constraints |
|---|---|---|
| `id` | UUID | Primary key |
| `user_id` | UUID | Not null, FK → `users.id` `ON DELETE CASCADE` |
| `account_id` | UUID | Not null, FK → `financial_accounts.id` `ON DELETE CASCADE` |
| `category_id` | UUID | Nullable, FK → `transaction_categories.id` `ON DELETE SET NULL` |
| `amount` | numeric(14,2) | Not null, must be non-zero |
| `currency` | varchar(3) | Not null |
| `description` | varchar(255) | Not null |
| `merchant` | varchar(120) | Nullable |
| `occurred_on` | date | Not null |
| `transaction_type` | varchar(12) | Not null; `income`, `expense` or `transfer` |
| `source` | varchar(12) | Not null, default `provider`; `provider` or `manual` |
| `external_id` | varchar(128) | Nullable; provider identifier |
| `dedupe_key` | varchar(64) | Not null; SHA-256 hex digest |
| `is_pending` | boolean | Not null, default `false` |
| `notes` | varchar(500) | Nullable |
| `created_at`, `updated_at` | timestamptz | Not null, default `now()` |

Constraints and indexes:

- Check `amount <> 0` (`ck_transactions_amount_nonzero`).
- Unique `(account_id, dedupe_key)` —
  `uq_transactions_account_dedupe`.
- `ix_transactions_user_id`, `ix_transactions_account_id`,
  `ix_transactions_category_id`, `ix_transactions_occurred_on`.
- `ix_transactions_user_date` on `(user_id, occurred_on)`.
- `ix_transactions_user_type` on `(user_id, transaction_type)`.

Provider deduplication uses `sha256("<account_id>:<external_id>")`. Manual
deduplication hashes account, date, amount, lower-cased description and
lower-cased merchant. `allow_duplicate=true` appends a random suffix so a second
manual entry can be stored.

## Phase 3: financial intelligence

All Phase 3 tables carry `created_at` and `updated_at` (`timestamptz`, not null,
default `now()`) except `forecasts`, which has `generated_at` instead of a
`created_at`/`updated_at` pair. Every table except `transaction_categories`
references owner data; every query is scoped by `user_id`.

### `budgets`

A spending limit for a date range, optionally for one category.

| Column | Type | Constraints |
|---|---|---|
| `id` | UUID | Primary key |
| `user_id` | UUID | Not null, FK → `users.id` `ON DELETE CASCADE` |
| `category_id` | UUID | Nullable, FK → `transaction_categories.id` `ON DELETE SET NULL`; `NULL` means overall spending |
| `name` | varchar(120) | Not null |
| `period_start` | date | Not null |
| `period_end` | date | Not null |
| `amount` | numeric(14,2) | Not null, must be positive |
| `currency` | varchar(3) | Not null |
| `alert_threshold` | integer | Not null, default `80`; API range 0–100 |
| `is_active` | boolean | Not null, default `true` |
| `created_at`, `updated_at` | timestamptz | Not null, default `now()` |

Constraints and indexes:

- Check `amount > 0` (`ck_budgets_amount_positive`).
- Check `period_end >= period_start` (`ck_budgets_period_end_after_start`).
- `ix_budgets_user_id`,
  `ix_budgets_user_period` on `(user_id, period_start, period_end)`,
  `ix_budgets_user_active` on `(user_id, is_active)`.

Overlapping active budgets in the same category and currency are rejected by
`BudgetService` (`409 budget_period_overlap`); there is no database exclusion
constraint for overlap.

All user-owned rows cascade on user deletion. Connections cascade to their
accounts, consents and sync jobs; accounts cascade to transactions; bills and
subscriptions cascade to their payments. Category deletion sets the referencing
column to `NULL`. Deleting a user is not exposed by the API.

`0003_phase3_intelligence` is the Alembic head.

**Current development database state:** the local PostgreSQL database is at
`0003_phase3_intelligence`. All five Phase 3 tables exist and are empty, and
`alembic check` reports `No new upgrade operations detected` (24 November 2026).

The revision was applied by the Docker backend's startup command
(`alembic upgrade head && uvicorn ...`), not by an approved manual migration.
That makes every backend restart a potential migration: an un-reviewed revision
in the working tree is applied automatically the next time the container
starts. Treat this as a known risk; see
[Docker startup applies migrations](#docker-startup-applies-migrations).

Expected verification commands (read-only except `upgrade`):

```powershell
# From backend/, with the target database reachable
.\.venv\Scripts\alembic current          # expect 0003_phase3_intelligence (head)
.\.venv\Scripts\alembic upgrade head     # no-op while already at head
.\.venv\Scripts\alembic check            # expect "No new upgrade operations detected"
```

Before applying any future revision, take a backup first:

```powershell
docker exec ai-payment-guardian-db-1 pg_dump -U guardian -d guardian `
  --format=custom --no-owner --no-privileges --file=/tmp/guardian-backup.dump
docker cp ai-payment-guardian-db-1:/tmp/guardian-backup.dump .\guardian-backup.dump
```

`alembic upgrade head --sql` only prints PostgreSQL DDL; it performs no writes
and was used to verify revision `0003` offline.

### Docker startup applies migrations

Both `docker-compose.yml` (`backend.command`) and `backend/Dockerfile` (`CMD`)
run `alembic upgrade head` before starting Uvicorn. Consequences:

- Starting or rebuilding the stack silently applies any pending revision found
  in `backend/migrations/versions/`, with no approval step and no automatic
  backup. This is how revision `0003_phase3_intelligence` reached the
  development database.
- A `downgrade` survives only until the next restart, which re-applies `head`.
- A broken revision blocks the API from starting, because the migration runs
  first.

The proposed safer workflow, **not applied yet**, is:

1. Remove `alembic upgrade head` from the container command so startup only
   serves the application.
2. Migrate explicitly, in a deliberate step, after a verified backup and after
   the pending revision has been reviewed and `alembic check` is clean.
3. Let the application fail fast, or expose a health check that reports a stale
   schema, when the database is behind the expected revision, instead of
   migrating itself.

Rules for later phases:

1. Generate a new revision; never modify an applied migration.
2. Keep model and migration changes in the same commit.
3. Run `alembic check` to confirm there is no schema drift.
4. Run tests against PostgreSQL before merging.
